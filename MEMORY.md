# MEMORY.md

## Memo

- `lip.sln` exists at the repo root and currently includes the main code projects under `src/` plus test projects under `tests/`; `Lip.Installer` is referenced by the release workflow but its project files may not always be present in the working tree.
- `Lip.Cli/Program.cs` is a thin Spectre.Console front end; most operational wiring happens in `LipClient.Create`, which constructs `ConfigService`, `CacheService`, `SourceService`, `WorkspaceService`, `PackageInstaller`, `CompositePackageRegistry`, and `InstallService`.
- Workspace state is persisted in `tooth_lock.json` in the current working directory; it stores installed package manifests, variant labels, explicit/implicit status, and tracked file paths.
- Global runtime config is persisted in `liprc.json` under `Environment.SpecialFolder.ApplicationData` in `lip/liprc.json`; cache and temp data live under `Environment.SpecialFolder.LocalApplicationData` in `lip/cache` and `lip/temp`.
- `tooth.json` is the package manifest and `lip init` creates a minimal one, but current install/uninstall flows do not mutate `tooth.json`; they operate on workspace files plus `tooth_lock.json`.
- Durable docs caveat: `docs/faq.md` matches the current implementation on `tooth.json`, but `docs/intro/quick_start.md` still says install/uninstall update the manifest; trust the code and FAQ over that quick-start wording.
- Manifest, runtime config, and workspace state all use format version `3` with UUID `289f771f-2c9a-4d73-9f3f-8492495a924d`.
- Package argument parsing in `LipClient` tries, in order: exact `PackageSpec`, flexible `PackageId`, local archive path, then remote archive URL.
- Package source retrieval prefers Go module proxy first and Git second; download URLs may be rewritten through `github_proxy`, and `go_module_proxy` defaults to `https://goproxy.io`.
- Git fallback currently caches cloned repositories as directories via `CacheService.GetOrCreateDirectory`; this is fragile because `.git` contents can make `cache clean` deletion fail and directory-structured cache entries are riskier than file-archive cache artifacts.
- Package registry lookup is layered: installed workspace packages first, then remote registries (`GoModuleProxyPackageRegistry`, `LiprPackageRegistry`, `GitPackageRegistry`), then source-derived manifests.
- With dependencies enabled, install/uninstall/update recompute the full desired dependency graph from explicitly installed packages, uninstall removed packages in reverse topological order, then install new ones in topological order.
- `--no-dependencies` bypasses dependency solving and is explicitly treated as potentially leaving a broken workspace.
- Package variants are merged by label and current RID platform match; platform matching supports glob patterns and requires at least one full label+platform match.
- Package install order is: run pre-install scripts, place asset files, run install/post-install scripts, then record workspace state. Uninstall runs pre-uninstall/uninstall scripts, removes tracked files except `preserve_files`, applies `remove_files`, runs post-uninstall scripts, then removes state.
- CI expectations for code changes are `dotnet format --verify-no-changes lip.sln` and `dotnet test lip.sln`; docs are a separate VitePress project under `docs/` built with `pnpm build`.
- Docs tooling now uses `pnpm`; `docs/` should keep `package.json` plus `pnpm-lock.yaml`, not `package-lock.json`, and docs verification should be run with `pnpm build`.
- Native npm distribution is driven from `npm/`; the single `@futrime/lip` package exposes root launchers `lip.js` and `lipd.js`, bundles both `lip` and `lipd` for all six supported platforms in root-level platform folders like `linux-x64/` and `win32-x64/`, and the release workflow rewrites the package version from the release event tag before publishing.
- The published winget manifest for `futrime.lip` `0.34.3` declares `Dependencies.PackageDependencies: Microsoft.DotNet.Runtime.10`; the npm package now bootstraps .NET Runtime 10 in `postinstall.js` by silently invoking the official `dotnet-install` scripts on all supported platforms, and `npm/lip.js` plus `npm/lipd.js` set `DOTNET_ROOT` to the default install root when a user-level runtime is present.
- Public install docs now standardize on the npm package for all platforms, documenting both `npm install -g @futrime/lip` and one-off `npx @futrime/lip ...` usage; Windows-only alternatives are limited to `winget` and release `setup.exe`, and the old `scripts/install.sh` plus build-from-source installation docs were removed.

- CLI presentation: `lip list --json` emits real snake_case JSON, the CLI sets `Console.OutputEncoding` to UTF-8, and operational output goes to standard error so `--json` output on standard output stays pipeable. Unhandled exceptions print one line plus the path of a per-run log under `%LOCALAPPDATA%\lip\logs` (newest 10 kept, proxy credentials redacted). `install`/`uninstall`/`update` print a plan preview grouped under `Requested`/`Dependencies`, a past-tense `[n/N] installed|removed <pkg>` line after each package completes (the `--no-dependencies` branches print steps and the closing summary too), and an `installed/removed N packages in Xs` summary. Each transfer renders interactively as two live lines — the URL as an OSC 8 hyperlink over a solid-block bar (`█`/`░`, custom `ProgressColumn`) carrying one percentage, bytes and a smoothed speed — and both lines are erased when the transfer finishes, so nothing on screen claims to still be installing. The durable trail is a past-tense `Downloaded <size> from <url>` line printed after the progress region ends; `TextLinker.Linkify` turns every URL into a hyperlink and escapes all other text, so script output cannot break markup. Non-interactive output skips live bars entirely. Still unfixed: a long-running install script leaves the terminal without live feedback (only `--verbose` streaming would fix that), help text is half localized, `versions` and `view` have no `--json`, `docs/cli/overview.md` advertises global `--json`/`--verbose` options that do not exist, git subprocess failures surface only as lip's own message with the reason in the log, `lip install mypkg.zip` parses as a package ID before a local path, and the CLI has no test project so command output is verified by hand or with the probe harness below.
- Live progress rendering traps in the CLI, each one already hit once: the hyperlink *target* must be the full URL while only the displayed text may be shortened (`TextLinker.Fit` keeps both ends), because truncating the target makes clicking open a wrong address; the bar width has to be derived from the console width (`ProgressColumn` gets it by constructor) so the line never wraps, since a wrapped line breaks the live region's cursor accounting and leaves fragments on screen; a durable line must never be printed from inside `RunWithProgress`, because writing to the console during a live region writes into the region and the next refresh overwrites it; `ProgressTask.Value` is clamped by `MaxValue`, so a transfer whose length the server does not announce uses `MaxValue = double.MaxValue` with `IsIndeterminate = true` and carries the byte count in `Value` (the earlier `IsIndeterminate()` + `Increment(1)` rendered `100% 1 B / 1 B`, and `MaxValue = 0` pins `Value` to zero); a percentage must appear once per line or narrow terminals wrap; and progress accuracy requires the Downloader library's `ReceivedBytesSize` (cumulative), while `ProgressedByteSize` is only the per-event delta. A shared progress region was tried and reverted because Spectre cannot remove finished tasks from a region, and `AddTask` rejects an empty task name.
- Verifying CLI rendering: redirecting the CLI's output cannot show the live region, because Spectre detects a non-interactive stream and skips it, so `awk`-style checks on captured output only ever see the durable lines. To inspect what a real terminal receives, build a `ConsoleUserInteraction` on a forced-interactive `IAnsiConsole` (`AnsiConsole.Create` with `Interactive = InteractionSupport.Yes`, `Ansi = AnsiSupport.Yes`, `Out = new AnsiConsoleOutput(StringWriter)` and a fixed `Profile.Width`) and read the raw escape stream; `.tmp/render-probe` holds such a harness (gitignored) with `widths` and `failure` modes that check line fitting per console width and that a thrown transfer still restores the cursor and clears the region. It also confirmed that `Markup.Escape` is the correct encoding for a `[link=...]` target containing markup characters.
- Package source fallback order: `SourceService.Get(PackageSpec)` tries the Go module proxies first and the git clone second. The clone uses `--branch v<version>` with no `--depth`, so the tag must be exactly `v`-prefixed and large repositories are cloned in full; the result is cached as a directory keyed by the canonical `git+https://<host>/<path>.git#v<version>` (not by the candidate that served it), and `GetCandidateUrls` supplies the candidates for both downloads and clones — every probed GitHub mirror as `{mirror}/{whole url}`, then direct access last. Two defects used to make this fallback unable to succeed at all and were fixed on 2026-09-20: the mirror URL was built with Flurl's `AppendPathSegments`, which dropped the `github.com` host (git answered `repository not found`), and the clone used only `FirstOrDefault(source => source is not null)`, so the `null` direct-access entry was always skipped and a mirror was used even when direct was fastest or every mirror was down. Verified with a real clone through a mirror (98 entries including `tooth.json`) and with unit tests asserting the exact clone URLs and the mirror→mirror→direct order.
- `DiagnosticLog.WriteException` walks the whole exception tree and appends the captured output of every `CommandFailedException` it finds, because a failed command's output is not part of any stack trace and the terminal only prints the one-line summary. This matters because `GitRunner` captures git's output (it used to be piped to the terminal) and `CommandRunner` captures script output, so without this the log said only `exit code 128`; the git reason (`fatal: repository ... not found`) and the URL lip actually tried now appear under an `--- output of the failed command: ... ---` heading.
- Manifest fields are optional but *absent* and *explicitly null* behave completely differently: every list/object property has an initializer, so omitting the key yields an empty collection, while a JSON `null` overwrites the initializer and crashes later with a bare `NullReferenceException` (`Object reference not set to an instance of an object.` on the terminal, `PackageManifest.GetVariant` line 98 in the log, no field name). Verified crashes on install for `scripts: null`, `remove_files: null`, `preserve_files: null`, `assets: null`, `placements: null` and `dependencies: null`; `urls: null` survives only because a `self` asset ignores it (a downloaded asset would hit `foreach (Url url in urls)`). Both install and uninstall go through `GetVariant`, so either command fails.
- Uninstall deletion (`PackageInstaller.BuildRemovalPlan` + `UninstallPackage`): the plan is computed before anything is deleted and holds the tracked files to remove, the ones already gone, the paths it refuses to touch and the `remove_files` matches; the delete step then only walks that plan. Guarantees added on 2026-09-20: **nothing outside the current workspace is ever deleted** — a lockfile path outside it is mapped back through the package's own placement `dest` values (longest destination first, and only when the mapped file exists) and is otherwise reported instead of deleted, because guessing could hit the wrong file (note `GetWorkspaceRelativePath` returns a `..`-relative path for a sibling directory, so containment needs `IFileSystem.IsInsideWorkspace`, not a rooted-path check); `preserve_files` now also wins over a `remove_files` match, and a matched directory holding a preserved file is skipped whole; the workspace root and `tooth_lock.json` are protected from `remove_files`; and `SaveWorkspaceState` canonicalizes every recorded path, so a lockfile written by an older lip converges to workspace-relative paths on the first save. `--dry-run` prints the plan (`would delete N file(s) placed by the package`, the `remove_files` matches, kept paths) and the CLI no longer prints `removed`/success for it. `remove_files` matching was made strict on 2026-09-20 after it deleted real data: a pattern is now resolved against the workspace-relative path only, while `preserve_files` still also accepts the bare entry name (protecting too much is harmless, deleting too much is not). The bare-name fallback was what let `bds@1.26.40`, whose `remove_files` names root entries (`config`, `behavior_packs`, `resource_packs`, ...), also match `plugins/<plugin>/config` and `worlds/<level>/behavior_packs` and delete them with everything below; replaying it against an intact server copy produced 34 matches where the strict rule gives the 12 the author intended. A match that is, or holds, a file another installed package owns is left alone too (reported as `kept N path(s) because another installed package owns files there`), and every plan is written to the diagnostic log through `PrintVerbose` so a real uninstall can be audited afterwards. Still unchanged by design: a matched directory is removed with everything below it, tracked files have no reference counting, and uninstall scripts run arbitrary commands unless `--ignore-scripts`.
- `lip uninstall` (without `--no-dependencies`) works out what to keep by walking the dependencies recorded in the lockfile from the remaining explicitly installed packages (`GetReachableInstalledPackages`), so it consults no registry and never changes a version; `--no-dependencies` skips all of that and removes exactly what was named. It used to call `DependencySolver.Solve` there, which prefers the newest release satisfying each range, so a retained package whose range admitted a newer release was judged unnecessary and deleted while its replacement was never installed (`UninstallPackagesCore` has no `missingPackages` loop): on that server, `uninstall Advancements` deleted `Stats@0.8.1` and both `LegacyScriptEngine@0.18.2` variants that the retained `Server-2026#2025` still required, and it now removes exactly `Advancements`. A requirement naming only a package (no `#label`) counts as satisfied by any installed variant of it, because keeping a needed package beats deleting it.
- `lip update` accepts no package names: `UpdateEveryExplicitPackage` pre-checks every explicitly installed package with `GetLatestVersion`, prints `The following packages have newer versions available:` with `id  old → new` lines, then updates them one at a time by re-entering the single-package path. The per-package split is deliberate — one package in a set can be unresolvable and that must not fail the rest; each failure prints `⚠ Failed to update '<id>': …` with the exception in the log and the run continues. A named update pins every other explicit package to its installed version but lets implicit dependencies float to the newest satisfying release, so updating one plugin can also upgrade shared dependencies (`Glacie` on a real server drags `Stats` 0.8.1→0.8.3 and `LegacyScriptEngine` 0.18.2→0.18.5). `PackageInstaller.InstallPackage` checks `dryRun` *before* the already-installed check: an update replaces the installed version and a dry run performs none of the removals it describes, so without that every `lip update --dry-run` of a version bump failed with `Cannot install … because it is already installed with version …`.
- Manifest `assets[].type` handling (`PackageManifestAsset.AssetType`, dispatched in `PackageInstaller.InstallPackage`): five values — `self`, `tar`, `tgz`, `uncompressed`, `zip`. `self` takes the package's own source (`packageArtifact.Source`: Go module zip with the `module@version/` prefix stripped, local/remote archive, or the git checkout) and ignores `urls` entirely; `uncompressed` downloads the URL into `SingleFileSource`, whose only key is the empty string, so a file placement must use `src: ""`; a `src` naming the file itself (for example `src: "bedrock-server-1.26.40.8.zip"`) matches nothing and installs nothing **while still reporting success** (exit 0, zero files placed, lockfile records an empty file list); `src: "*"` also matches but the `dest` is then treated as a directory, so with an empty key the file lands on `dest` itself; `tar`, `tgz` and `zip` are the *same* code path (`isArchive: true` -> `ArchiveSource` -> `ArchiveFactory.OpenArchive`), so the declared archive label is documentation, not a validated format. Confirmed by experiment: declaring `tgz` for a zip works, `uncompressed` for a zip installs the archive verbatim without extraction, and `zip` for a text file fails with SharpCompress's `Cannot determine compressed stream type`. `dest` is validated against fully-qualified/rooted/`..` paths and is the *final* path: a `file` placement whose `src` equals the key copies to `dest` verbatim (so the file name has to be written into `dest`; `dest: "dl"` creates a file called `dl`, `dest: "dl/"` fails with `Could not find a part of the path`), while the glob branch appends the key's file name to `dest`. `dir` placements strip the `src` prefix and land under `dest` (a `..` relative path is skipped) but never work for `uncompressed`, because the empty key makes `Path.GetRelativePath` throw `The path is empty` at `PackageInstaller.InstallPackage`. Several placements can match one key and all of them copy. v2 manifests have no `type`: migration infers it from the asset URL's extension (`.tar`/`.tgz`/`.gz`/`.zip`, anything else `uncompressed`) and a missing URL becomes `self`.
- Known defect, confirmed with SharpCompress directly: a gzipped tar (`.tar.gz`, i.e. a `tgz` asset) cannot be installed at all. `ArchiveFactory.OpenArchive` — by path, by `FileInfo` or by stream — and `TarArchive.OpenArchive` and `GZipArchive` all fail on one (`Cannot determine compressed stream type`, or `Not a tar file`, or `Stream must be seekable`); only decompressing the gzip into a seekable buffer and then opening that works. This is invisible on Windows because the published `tgz` assets (for example bdsdown's linux-x64/arm64 and osx-* variants) target RIDs that never match here. `ArchiveSource` also reopens and re-scans the archive for every key (`Keys` then `OpenRead` per placed file), so placement cost grows with the entry count.
- Why a local or pinned install takes ~50 s while `--no-dependencies` takes ~1 s: with dependency solving enabled, `CompositePackageRegistry.GetAvailableVersions` merges results from *every* registry group, and `GoModuleProxyPackageRegistry.GetAvailableVersions` tries each Go proxy in order, treating any failure (including a 404, which means the module simply does not exist there) as a reason to continue. On this network `goproxy.cn` and `goproxy.io` answer 404 in under a second but `proxy.golang.org` is unreachable and stalls ~20 s+ per request, and there is no per-request timeout on the registry HTTP calls; `LiprPackageRegistry` then re-downloads the whole `https://lipr.levimc.org/index.json` per call with no cache, and `GitPackageRegistry` runs `git ls-remote` after that. The manifest itself is already in hand from `ArtifactsPackageRegistry`, so the remote registries are consulted even when the requested exact version came from a local package.

- Manifest template handling in `PackageManifestMigration`: v3 manifests render both `{{name}}` (Scriban) and the legacy `$(name)` form, and `$(name)` is substituted only when `name` resolves to a field of the manifest itself. Accepting every `$(...)` would let Scriban's builtins replace unrelated text, for example turning `echo $(date)` in a script into a Scriban object dump. The v2 to v3 migration model only carries `version` and `path`, while v3 rendering uses the whole document, so `$(info.name)` works in v3 but not in migrated v2 manifests.
- Packaging can be verified locally on Windows for all six CI runtimes at once: `dotnet publish <project> -o .tmp/artifacts/<rid> -r <rid> --no-self-contained -p:DebugType=embedded -p:Version=<version>` cross-publishes linux-x64/arm64 and osx-x64/arm64 without the CI matrix, `.tmp/` is gitignored, and `inno/lip.iss` reads binaries from `.tmp/artifacts`. Only win-x64/win-arm64 output can actually be executed on this machine; the rest are build-verified only.
- `dotnet format --verify-no-changes lip.sln` cannot pass on a Windows checkout of this repo while `core.autocrlf=true`: every file reports `ENDOFLINE`. `git ls-files --eol` shows `i/lf w/crlf` for untouched files too, so this is a checkout artifact rather than a code problem; verify formatting by passing `--include <changed files>` and ignoring ENDOFLINE.
- `pnpm build` inside `docs/` fails on this machine before VitePress runs: pnpm's deps-status check re-runs `pnpm install`, which exits 1 with `ERR_PNPM_IGNORED_BUILDS` (`esbuild@0.27.4` has an unapproved build script). The docs themselves are fine — run `node node_modules/vitepress/bin/vitepress.js build` from `docs/` instead, or approve the build with `pnpm approve-builds`.
- `Lip.Core.Tests` is fully offline and finishes in about 300 ms, while `Lip.Core.RegressionTests` performs real network calls (lipr, git, GitHub, Go proxies) and takes 5-20 minutes depending on retries. Several of its tests are unreliable on this machine: `GitRunnerTests` and `GitPackageRegistryTests` need a working git path (git's global `http.proxy` points at `socks5://127.0.0.1:7890`, which is only up when the user's proxy client runs, while the Windows system proxy is disabled — `ProxyEnable=0` — so lip's own HTTP downloads go direct and work while git fails), and `FileDownloaderTests` fetches `raw.githubusercontent.com`, which is slow and intermittent here. `GoModuleProxyPackageRegistryTests` used to hard-code `https://proxy.golang.org`, which never answers from this network and made four tests permanently red; it now uses `ProxySelector.DefaultGoModuleProxies[0]` (goproxy.cn) so the four pass in about a second.
- Proxy auto-selection: `ProxySelector` probes candidates in parallel (2 s timeout) and orders them by latency, cached for 24 h in `%LOCALAPPDATA%\lip\proxy-selection.json`; GitHub candidates include a null entry meaning direct access, so overseas users keep direct while mirrors win where direct is slow. `github_proxy`/`go_module_proxy` set to a URL fixes the choice and skips probing; `github_mirrors`/`go_module_mirrors` add user candidates and are entered comma-separated via `lip config set`. `go_module_proxy` defaults to null (= auto) since this change. Caution: an older lip binary writing `liprc.json` fills the old default (`proxy.golang.org`) back in, silently disabling auto mode. Built-in GitHub mirrors: gh-proxy.com, ghproxy.net, ghfast.top, github.akams.cn, ghproxy.homeboyc.cn, github.bibk.top; built-in Go proxies: goproxy.cn, goproxy.io, proxy.golang.org.
- Durable docs caveats beyond the `tooth.json` one: `docs/cli/overview.md` advertises global `--json` and `--verbose` options that do not exist, `docs/guides/internal_mechanism.md` says workspace state lives in a `.lip` directory (it is `tooth_lock.json` in the working directory) and points at `schemas/tooth.v3.schema.json`, which is actually `schemas/manifest.schema.json`.
- `tooth_lock.json` stores package file paths relative to the workspace root with forward slashes; lockfiles written by older versions hold absolute paths and are still accepted on read, so both forms must keep working. This format change alters uninstall behaviour across copies: with the released (absolute-path) build, uninstalling inside a *copy* of a workspace deletes nothing in the copy but silently deletes the tracked files in the ORIGINAL directory, while the current build deletes them in the copy and leaves the original alone (verified with both binaries on the same package). The same comparison shows the current build honours `preserve_files` where the released build did not: with `preserve_files` covering `config.json` and `data/**`, the released build deleted both despite the patterns (it matched the globs against the bare file name only) and the current build kept them.
- Windows `setup.exe` now installs the .NET Runtime 10 prerequisite online during `PrepareToInstall`: it first checks `HKLM32\SOFTWARE\dotnet\Setup\InstalledVersions\<arch>\InstallLocation` for `Microsoft.NETCore.App\10.*`, falls back to the default arch-specific global path if needed, then downloads `Runtime/10.0/latest.version` from `builds.dotnet.microsoft.com` and silently runs the matching official `dotnet-runtime-<version>-win-{x64|arm64}.exe` with `/install /quiet /norestart`.
